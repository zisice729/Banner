# Banner消费端系统 - 技术方案

## 一、业务背景

### 1.1 业务场景

运营端（B端）管理系统负责创建和管理Banner资源位，每个Banner可关联一个人群包（指定可见用户列表）。C端用户在App内请求Banner时，需要根据业务线、日期和用户ID快速返回命中的Banner列表。

### 1.2 核心诉求

| 诉求 | 说明 |
|------|------|
| **高性能读取** | C端请求量大，需毫秒级响应 |
| **人群包支持** | Banner可指定可见用户列表，支持数十万级用户 |
| **数据最终一致** | 运营端修改后，C端需在秒级内感知变更 |
| **高可用** | 缓存故障时仍可降级提供服务 |

### 1.3 系统定位

本系统是**Banner缓存同步与查询服务**，不写入业务数据，职责为：

- 接收运营端Kafka消息，RPC拉取完整数据，同步到Redis缓存
- 通过Caffeine本地缓存 + Redis二级缓存为C端提供高性能查询
- 通过XXL-Job定时任务保证缓存最终一致性

### 2.2 技术选型

| 组件 | 选型 | 说明 |
|------|------|------|
| 消息队列 | Kafka | 单一Topic，type字段区分消息类型 |
| 分布式缓存 | Redis | 主缓存，分桶存储人群包 |
| 本地缓存 | Caffeine | 二级缓存，减少Redis访问 |
| 缓存一致性 | Redis Pub/Sub | 广播本地缓存失效 |
| 分布式锁 | Redis + Lua | 保证同一Banner缓存更新串行执行 |
| 定时任务 | XXL-Job | 增量同步 + 全量一致性检查 |
| 幂等存储 | H2内存数据库 | MQ消费记录，messageId唯一索引 |
| RPC调用 | RestTemplate | 调用运营端获取数据 |

## 三、核心流程

### 3.1 缓存同步流程（MQ消费）

```
运营端写DB完成
    │
    ▼
BannerMqProducer.sendBannerSync(id)
    │  发送消息: {messageId: UUID, id: 123, type: 1}
    ▼
Kafka Topic: banner-sync-topic
    │
    ▼
BannerSyncConsumer.consume()
    │
    ├─① 幂等检查
    │    INSERT mq_consume_record(message_id, banner_id)
    │    ├─ 成功 → 继续
    │    └─ DuplicateKeyException → 已消费，跳过
    │
    ├─② type=DELETE → 删除缓存，结束
    │
    ├─③ 加分布式锁
    │    tryLockWithRetry("banner:123:lock")
    │
    ├─④ RPC获取Banner基本信息
    │    BannerOperationClient.getBannerById(123) → BannerSyncRequest
    │
    ├─⑤ 分页RPC获取用户列表
    │    while (hasNext):
    │        BannerOperationClient.getUserIdsByPage(123, page, 5000)
    │
    ├─⑥ 更新缓存
    │    BannerCacheManager.refreshBannerCache(123, data)
    │    ├─ SET banner:123:info → Banner JSON
    │    ├─ 遍历userIds，按 userId % 1000 分配到桶
    │    │    SADD banner:123:users:{bucketIndex} userId
    │    ├─ 无人群限制 → SADD banner:no_user_list 123
    │    ├─ SADD banner:product:1:date:20260607 → 123
    │    └─ PUBLISH banner:cache:invalidate → "123"
    │
    └─⑦ 释放锁
         unlock("banner:123:lock", lockValue)
```

### 3.2 查询流程

```
C端请求: GET /api/banners?productId=1&date=20260607&userId=10086
    │
    ▼
BannerController.getBanners(BannerQueryRequest)
    │
    ▼
BannerQueryService.getBannersByProductDateAndUserId(1, "20260607", 10086)
    │
    ├─① 获取该产品+日期下的所有Banner
    │    BannerCacheManager.getBannersByProductAndDate(1, "20260607")
    │    ├─ Caffeine本地缓存命中 → 返回
    │    └─ 未命中 → Redis SMEMBERS banner:product:1:date:20260607
    │              → 逐个获取 banner:{id}:info → 回填本地缓存
    │
    └─② 人群包过滤
         BannerCacheManager.containsUserId(id, 10086)
         ├─ SISMEMBER banner:no_user_list {bannerId}
         │    → 存在 → 对所有用户可见
         └─ 不存在 → bucketIndex = 10086 % 1000
              SISMEMBER banner:{id}:users:{bucketIndex} "10086"
```

### 3.3 本地缓存一致性流程

```
机器A更新Redis缓存
    │
    ▼
PUBLISH banner:cache:invalidate "123"
    │
    ├─→ 机器A CacheInvalidationListener.onMessage() → 清除本地缓存
    ├─→ 机器B CacheInvalidationListener.onMessage() → 清除本地缓存
    └─→ 机器C CacheInvalidationListener.onMessage() → 清除本地缓存
    │
    ▼
下次请求时从Redis重新加载到本地缓存
```

### 3.4 定时任务流程

```
XXL-Job调度中心
    │
    ├─ incrementalSyncJob（增量同步，每5分钟）
    │    │
    │    ▼
    │    RPC: BannerOperationClient.getIncrementalUpdatedIds(sinceTime)
    │    │
    │    ▼
    │    逐个调用 BannerCacheManager.refreshBannerCache(id, data)
    │
    └─ fullConsistencyCheckJob（全量一致性检查，每天凌晨）
         │
         ▼
         RPC: BannerOperationClient.getAllActiveBannerIds()
         │
         ▼
         对比Redis缓存，修复不一致数据
```

## 六、Redis存储设计

### 6.1 Key规范

所有Key通过`RedisKeyBuilder`使用`String.format`统一管理：

| Key模板 | 类型 | 说明 |
|---------|------|------|
| `banner:%d:info` | String | Banner基本信息JSON |
| `banner:%d:users:%d` | Set | 用户ID分桶（固定1000个桶，取模定位） |
| `banner:no_user_list` | Set | 无人群限制的Banner ID集合 |
| `banner:%d:lock` | String | 分布式锁 |
| `banner:product:%d:date:%s` | Set | 按产品+日期索引Banner ID |

### 6.2 Pub/Sub频道

| 频道 | 消息体 | 说明 |
|------|--------|------|
| `banner:cache:invalidate` | bannerId(String) | 本地缓存失效通知 |

### 6.3 分桶策略（取模定位，O(1)查询）

| 配置项 | 值 | 说明 |
|--------|-----|------|
| USER_BUCKET_COUNT | 1000 | 固定桶数量，用于取模定位 |
| USER_BUCKET_SIZE | 5000 | RPC分页大小 |

**查询流程（O(1)复杂度）**：

```
containsUserId(id, userId):
    → 快速判断：SISMEMBER banner:no_user_list {bannerId}
    → 如果在无用户限制集合中 → 返回true
    → 否则：bucketIndex = userId % 1000
    → SISMEMBER banner:{id}:users:{bucketIndex} userId
```

**写入流程**：

```
遍历每个userId
    → bucketIndex = userId % 1000
    → SADD banner:{id}:users:{bucketIndex} userId
```

**固定桶数量优势**：
- **一致性**：缓存刷新后，同一userId的桶位置不变
- **查询O(1)**：取模一次定位，无需遍历
- **简单**：不需要存储桶数量

## 九、幂等机制

```
消费者收到消息
    │
    ▼
INSERT mq_consume_record(message_id="uuid-xxx", banner_id=123)
    │
    ├─ INSERT成功 → 首次消费，继续处理
    │
    └─ DuplicateKeyException → 同一messageId已存在，说明已消费过，跳过
```

**设计要点**：
- 每条MQ消息携带唯一`messageId`（UUID），由生产者生成
- `mq_consume_record`表使用H2内存数据库，`message_id`为主键
- 同一Banner的不同更新消息，messageId不同，不会误判
- 同一消息重复投递，messageId相同，主键冲突跳过

## 十、并发控制

### 10.1 分布式锁

消费者处理同一Banner时加分布式锁，保证缓存更新串行执行：

```
lockKey = "banner:{id}:lock"

tryLockWithRetry(lockKey)
    ├─ 首次尝试：SETNX，TTL=30s
    ├─ 重试：指数退避（100ms → 300ms → 900ms → ...）
    └─ 最多重试5次

unlock(lockKey, lockValue)
    └─ Lua脚本原子释放（校验lockValue后删除）
```

### 10.2 缓存更新原子性

在分布式锁保护下，Banner信息和用户列表作为一个整体更新：

1. 删除旧用户桶
2. 分页RPC获取用户列表并分桶写入
3. 更新Banner信息缓存
4. 更新产品+日期索引
5. 发布本地缓存失效通知
